# АУДИТ ТОРГОВОЙ ЛОГИКИ И РЕКОМЕНДАЦИИ ПО УЛУЧШЕНИЮ (ДЛЯ MIMO V 2.5)

**Контекст:** Аудит торгового бота (версия 2.5.0, стратегия ICT), проведенный для выявления уязвимостей, логических ошибок и сомнительных параметров с целью последующего рефакторинга моделью Mimo v 2.5 в OpenCode.

---

## 1. КРИТИЧЕСКИЕ ЛОГИЧЕСКИЕ ОШИБКИ И БАГИ (HIGH PRIORITY)

### 1.1. Уязвимость Confirmation Score (Gate Phase 1.4)
* **Проблема:** В `PatternEngine` для прохождения фильтра `_conf_score` требуется минимум 2 балла. При этом наличие BOS само по себе дает 2 балла. Это означает, что **любой сетап типа Continuation автоматически проходит проверку**, даже если нет подтверждающих факторов (Order Block или FVG). Это делает этот Gate бессмысленным для трендовых продолжений.
* **Решение:** 
  * Изменить логику оценки: поднять минимальный порог `_conf_score` до 3, чтобы требовать `BOS (2) + FVG (1)` или `BOS (2) + OB (1)`.
  * *Альтернатива:* Ввести отдельный порог для Continuation (минимум 3) и Reversal (минимум 2).
* **Файл для изменений:** `strategy/pattern_engine.py`

### 1.2. Неработающий флаг `block_neutral_htf` (Gate Phase 1.45)
* **Проблема:** В конфигурации (AppConfig) заявлен флаг `block_neutral_htf = true`, однако в документации указано: "Если HTF bias = neutral: пропускает всё (нет directional confirmation)". Фактически нейтральный старший таймфрейм игнорирует флаг блокировки и разрешает любые входы, снижая винрейт в периоды консолидации.
* **Решение:** 
  * Добавить явную проверку флага в `HTF Bias Gate`: 
    `if htf_bias == neutral and config.block_neutral_htf: return None # HTF_NEUTRAL_BLOCKED`
* **Файл для изменений:** `strategy/htf_bias.py` (или модуль пайплайна, отвечающий за Phase 1.45).

### 1.3. Утечка Cooldown в режиме `ob_aware` (Gate Phase 0.1 / Phase 6)
* **Проблема:** Ранний сброс кулдауна `if cooldown_mode == 'ob_aware': return False, 0` пропускает проверку на Фазе 0.1. Однако, если на графике вообще не сформирован Order Block (OB), логика сравнения `last_ob.midpoint` на Фазе 6 может сломаться или пропустить дублирующийся сигнал (spamming). 
* **Решение:** 
  * На Фазе 0.1 проверять: `if cooldown_mode == 'ob_aware' and has_recent_ob: ...`
  * На Фазе 6 добавить fallback: если `ob_aware` включен, но OB для сравнения отсутствует, применять правила `strict` cooldown.
* **Файл для изменений:** `scheduler/scanner.py` (Phase 0.1 и Phase 6).

## 2. СОМНИТЕЛЬНЫЕ ПАРАМЕТРЫ И РИСК-МЕНЕДЖМЕНТ (MEDIUM PRIORITY)

### 2.1. Искаженная логика Келли (Phase 4: Risk Engine)
* **Проблема:** Использование формулы Келли ограничено сверху параметром `base_risk_pct` (1.0% по умолчанию): `risk_pct = min(kelly * 100, base_risk_pct)`. Формула Келли математически предназначена для максимизации сложного процента при наличии edge (преимущества). Ограничивая Келли базовым риском, бот использует эту метрику исключительно как пенальти для неуверенных сделок, теряя весь потенциал максимизации прибыли на "верных" сетапах.
* **Решение:** 
  * Ввести параметр `max_kelly_risk_pct` (например, 2.5% или 3.0%).
  * Логика: `risk_pct = clamp(min_risk_pct, kelly * 100, max_kelly_risk_pct)`.
* **Файл для изменений:** `risk/engine.py`

### 2.2. Слишком жесткий фильтр волатильности (Phase 0.4)
* **Проблема:** Условие отмены сканирования при `ATR > 5.0%`. Для крипторынка (особенно альткоинов типа SOL/USDT) волатильность выше 5% на таймфреймах 1h/4h является нормой в периоды сильных трендов. Бот может блокировать самые профитные трендовые движения (Expansion Phase).
* **Решение:** 
  * Сделать верхний порог динамическим в зависимости от актива (например, для BTC 5% адекватно, для SOL лучше 8-10%) или привязать к `volatility_regime.py` (не отключать бота, а снижать размер позиции через `vol_adj`).
* **Файл для изменений:** `config/settings.py` (параметр `VOLATILITY_MAX_ATR_PERCENT`).

### 2.3. Статичный ATR-буфер для Stop Loss (Phase 1.5)
* **Проблема:** Добавление фиксированного `atr * 0.35` к Invalidation level может быть недостаточным. Market makers часто сносят ликвидность на 0.5 - 0.75 ATR за свингом. 35% от ATR на 1h/4h графике криптовалют часто приводит к выбиванию позиции тенью (whipsaw).
* **Решение:** 
  * Использовать множитель от 0.5 до 1.0 в зависимости от текущей фазы рынка (если `HIGH_VOL` -> буфер шире).
* **Файл для изменений:** `strategy/trade_engine.py`

## 3. АРХИТЕКТУРНЫЕ УЛУЧШЕНИЯ ДЛЯ УВЕЛИЧЕНИЯ ВИНРЕЙТА (LOW PRIORITY)

### 3.1. Аддитивная оценка Probability Engine (Phase 3)
* **Проблема:** Использование базового значения 50.0 с прибавлением констант (например, +3.0 за Sweep, +4.0 за MSS) математически не обосновано и может привести к "переоценке" сетапов (overconfidence). Накопление бонусов без учета их ковариации искажает вероятность (P(TP)).
* **Решение:** 
  * Перейти к мультипликативной скоринговой модели (Наивный Байес) или весам, нормированным через функцию `Sigmoid`. 
  * До завершения сбора 100+ сделок для XGBoost, лучше использовать консервативную формулу оценки, чтобы EV Gate (`NEGATIVE_EV`) не пропускал сделки на ложной уверенности.
* **Файл для изменений:** `strategy/probability_engine.py`

### 3.2. Интеграция Premium/Discount зон (AppConfig)
* **Проблема:** Флаг `PREMIUM_DISCOUNT` отключен (`false`), так как "A/B показал ухудшение (PF 1.28->0.91)". Ухудшение, вероятно, связано с тем, что строгий фильтр PD отрезает хорошие входы на агрессивных трендах. 
* **Решение:** 
  * Не использовать PD как жесткий блокиратор (Hard Gate), но интегрировать его как `soft multiplier` в `Probability Engine`. Покупка в Premium-зоне должна снижать размер позиции, а не отменять сделку полностью, если тренд сильный.
* **Файл для изменений:** `strategy/weight_manager.py` и `config/settings.py`

### 3.3. Логика исполнения свечей (`df.iloc[:-1]`)
* **Проблема:** Исключение открытой свечи правильно для избежания перерисовки. Однако на таймфрейме 4h это означает задержку входа до 4 часов после формирования паттерна.
* **Решение:** 
  * Внедрить `multi_tf` режим как стандарт: контекст и паттерны считаются по закрытым 1h/4h свечам, но триггер входа ищется на текущем 5m графике по формирующемуся price action в реальном времени.

---
**Итог для модели Mimo v 2.5:** Начните рефакторинг с исправления пунктов 1.1 и 1.2 (патч для `pattern_engine.py` и `htf_bias.py`), затем переработайте логику расчета кулдауна (1.3) и снимите жесткие лимиты Келли (2.1).
