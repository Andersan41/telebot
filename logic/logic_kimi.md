## 1. P0 — КРИТИЧЕСКИЕ (логические конфликты / потенциальные баги)

### [LG-01] Конфликт «структурного SL» и гейта `SL_ATR_CONFLICT` (min 2×ATR)
- **Где:** `strategy/trade_engine.py` (build_trade_plan) ↔ `risk/engine.py`.
- **Суть:** Trade Engine строит SL liquidity-first: `SL = invalidation.level − 0.35×ATR` (sweep low / OB low / swing / BOS). Risk Engine жёстко отклоняет, если `sl_distance < 2.0×ATR` (reason `SL_ATR_CONFLICT`, #41).
- **Обоснование на числах:** ATR = 1.0% от цены. Sweep low оказался в 0.9% от входа → корректный структурный SL = 0.9% + 0.35% = 1.25% ATR-экв. Гейт требует ≥ 2.0% → **reject**. При этом гейт `SL_TOO_TIGHT` уже стоит на 0.25%, а «мертвая зона» (2.0×ATR vs dynamic max = max(5%, 2.2×ATR)) слегка смягчена relaxed-режимом, но конфликт остаётся: бот либо массово режет сделки на **последней** стадии воронки (после выполнения всех дорогих фаз 1.5–4: HTF-запросы, overlays, 53 фичи), либо вынужден уширять SL за пределы реальной инвалидации — а тогда `RR ≥ 2.0` требует TP дальше, и режется уже `RR_TOO_LOW`.
- **Изменение (вариант А, рекомендуемый):** сделать ATR-гейт **нижней защитой, а не целью**:
  ```python
  # risk/engine.py
  min_sl_by_atr = atr * config.sl_atr_min_multiplier   # новый параметр, default 1.25
  if sl_distance < min_sl_by_atr:
      sl = entry - min_sl_by_atr          # расширить SL, НЕ reject
      tp = entry + (entry - sl) * min_rr  # пересчитать TP от нового SL
      if tp_beyond_structure:             # path clarity / opposing levels
          return reject(SL_ATR_CONFLICT)
  ```
  Вариант Б: понизить порог до `1.25–1.5×ATR` и оставить reject. Но тогда воронка продолжит тратить ресурсы на сделки, умирающие в конце — см. LG-01b.
- **[LG-01b] Перенести дешёвые гейты раньше:** `SL_ATR_CONFLICT`, `RR_TOO_LOW`, `NEGATIVE_EV` не зависят от фич/оверлеев — их предрасчёт (грубый SL/TP от ATR и инвалидации) можно выполнить сразу после Phase 1.5, до Phase 2–4. **Критерий приёмки:** доля `SL_ATR_CONFLICT`/`RR_TOO_LOW` в funnel summary падает; время цикла сканирования снижается; поведение остальных гейтов не изменилось (сверка reason-code распределения до/после на одних и тех же исторических данных за 7 дней).

### [LG-02] OB-aware cooldown молча обходится, если у сигнала нет OB
- **Где:** `scheduler/scanner.py` Phase 0.1 + Phase 6 (dedup).
- **Суть:** В режиме `ob_aware` (default) Phase 0.1 **всегда** пропускается; реальная проверка — сравнение `ob_midpoint` в Phase 6. В документе не описано поведение, когда у нового сигнала нет OB (continuation-сетап BOS+FVG) или у последнего сохранённого сигнала `ob_midpoint = NULL`. `CHECK-CODE`.
- **Обоснование:** если при отсутствии OB сравнение пропускается → сигнал проходит каждые 15 минут до истощения дневных лимитов (max 5 сделок/день сгорают на одном сетапе). Если при этом срабатывает BYPASS-ветка «different OB» — риск stacking коррелированных позиций (см. LG-10).
- **Изменение:**
  ```python
  # Phase 6 dedup, cooldown_mode == 'ob_aware'
  if last.ob_midpoint and new_ob:
      ...  # существующая логика midpoint-vs-ob_proximity_pct (0.5%)
  else:
      # fallback: строгий cooldown по направлению
      effective = max(base=45, tf_minutes * 2.0)
      if same_direction and delta < effective: block(DEDUP_SAME_DIR)
      elif cross_direction and delta < effective // 2: block(DEDUP_CROSS_DIR)
  ```
- **Критерий приёмки:** юнит-тесты на 4 комбинации (OB есть/нет × last/new), интеграционный тест: один и тот же символ без OB не порождает >1 сигнала за effective cooldown.

### [LG-03] Confirmation Score: вакуумный для continuation, ложно-режущий для reversal
- **Где:** `strategy/pattern_engine.py` (§6.4 исходного аудита), Phase 1.4–1.42.
- **Суть:** score = BOS(+2) + FVG(+1) + OB(+1), минимум 2.
  - **Continuation:** BOS обязателен гейтом `CONTINUATION_NO_BOS` → score ≥ 2 всегда → `CONFIRMATION_LOW` **недостижим** для continuation. Гейт-заглушка.
  - **Reversal:** обязательны sweep + displacement + MSS, но ни один из них не даёт очков. Сетап sweep+MSS+displacement **без** OB/FVG → score 0 → `CONFIRMATION_LOW`, хотя `require_entry_zone=false` (зона мягкая) и MSS — главный компонент разворота. При этом в Probability Engine MSS даёт +4, а здесь — 0. Противоречие внутри одной системы.
- **Изменение (выбрать один вариант и зафиксировать в конфиге):**
  ```python
  # Вариант А: score с учётом reversal-ядра
  score = 0
  if has_bos: score += 2
  if has_fvg: score += 1
  if has_ob:  score += 1
  if setup_type == "reversal" and has_mss: score += 2   # MSS — ядро reversal
  min_score = 3 if setup_type == "continuation" else 2   # continuation требует BOS+еще один компонент
  ```
  Вариант Б: оставить математику, но поднять минимум до 3 и добавить MSS+2 (эффект тот же для continuation, мягче для reversal).
- **Критерий приёмки:** для synthetic-фикстур: (a) continuation с BOS-only → блок; (b) continuation с BOS+FVG → проход; (c) reversal sweep+MSS+displacement без OB/FVG → проход; (d) reversal без MSS → блок раньше, на `MSS_NONE`.

### [LG-04] Два конфликтующих порога R:R — `min_rr_threshold=1.5` vs `min_rr_ratio=2.0`
- **Где:** `config/settings.py` TradingConfig ↔ RiskEngineConfig.
- **Суть:** `TradingConfig.min_rr_threshold` (env `MIN_RR_THRESHOLD`, default 1.5) и `RiskEngineConfig.min_rr_ratio` (env `RISK_ENGINE_MIN_RR`, default 2.0) дублируют друг друга; фактический гейт — 2.0 (со сдвигом на fees/slippage). Параметр 1.5 — мёртвый.
- **Изменение:** оставить один (`RiskEngineConfig.min_rr_ratio`), удалить второй из конфига и из всех обращений; либо явно развести семантику: `min_rr_threshold` — для построения TP в Trade Engine (цель построения), `min_rr_ratio` — для гейта (минимум к исполнению). Второе предпочтительнее, но тогда переименовать: `tp_target_rr` и `min_executable_rr`.
- **Критерий приёмки:** grep по коду показывает одно место истины; тест: сделка с RR 1.6 → `RR_TOO_LOW` (не «прошла»).

### [LG-05] Флаг `block_neutral_htf` существует, но не реализован
- **Где:** `config/settings.py` (AppConfig) ↔ Phase 1.45 HTF Bias.
- **Суть:** NEUTRAL HTF всегда пропускает (§28.6 исходного аудита). Флаг default `true` создаёт ложное ощущение защиты.
- **Обоснование:** при 4-TF голосовании (W1/D1/H4/H1) NEUTRAL — частый исход. Сейчас HTF-гейт фактически срабатывает только на явный конфликт направлений → его вклад в воронку мал, а вот в обучающую выборку попадает много сделок «без HTF-подтверждения».
- **Изменение (выбрать семантику):**
  ```python
  if htf_bias == NEUTRAL:
      if config.block_neutral_htf and setup_type == "continuation":
          return reject(HTF_NEUTRAL_BLOCKED)   # continuation без подтверждения тренда — не брать
      # reversal при NEUTRAL — разрешать (допустимая логика)
  ```
  Новый reason code `HTF_NEUTRAL_BLOCKED` — **добавить в конец** реестра (write-only правило: не переиспользовать и не удалять старые коды).
- **Критерий приёмки:** включение флага меняет funnel (появляется код `HTF_NEUTRAL_BLOCKED`); выключение — поведение как раньше.

### [LG-06] 4h-сетапы сканируются 4 раза в час на одной и той же закрытой свече
- **Где:** `scheduler/tasks.py` (cron `:02,:17,:32,:47`), `run_scan_cycle()`.
- **Суть:** 4h-свеча закрывается раз в 4 часа; сканы в :17/:32/:47 видят тот же набор закрытых свечей (последняя 4h-свеча не меняется). 3/4 циклов для 4h — повторная работа: повторные HTF-запросы (W1/D1/H4/H1 × 3 символа), повторные dedup-попытки, мусор в funnel-логе.
- **Изменение (вариант А):** per-TF расписание: 1h — каждые :02; 4h — раз в 4 часа :02. (Вариант Б, дешевле в переделке:) в `scan_symbol_v2` для tf=4h пропускать, если прошло < 3h 50m с последнего скана этого символа+TF (хранить `_last_scan[(symbol, tf)]`).
- **Критерий приёмки:** число fetch_ohlcv на 4h сокращается ~в 4 раза; число сигналов по 4h не меняется; funnel summary чистый.

## 2. P1 — СУЩЕСТВЕННЫЕ (качество сигналов и калибровка)

### [LG-07] Rules-based «P(TP)» — скор, а не вероятность; гейты `MIN_P_TP` почти не срабатывают
- **Где:** `strategy/probability_engine.py` + Phase 3.1.
- **Суть:** base 50 + аддитивные бонусы, кламп [20, 85]. Проблема в составе бонусов: **очки начисляются за компоненты, которые уже обязательны гейтами** — reversal: sweep(+3) + displacement(+3) + MSS(+4) = +10 → любой прошедший reversal-гейты сигнал стартует с ≥60. Плюс OB(+1.5)+FVG(+1)+armed(+1.5) → ~70–76. Пороги `min_p_tp`: buy 0.30 / sell 0.40 / reversal 0.50 — проходятся почти всегда. Гейт фактически вакуумный (как CONFIRMATION_LOW для continuation, см. LG-03).
- **Обоснование:** «вероятность» без калибровки по исходам — не вероятность: значения 0.55/0.65 не соответствуют ни одной частоте. Это опасно в двух местах: (1) EV-гейт и Kelly используют p как вероятность; (2) при переходе на ML режим смешанная школа (эвристика vs калиброванная модель) даст скачок поведения.
- **Изменение (этапами):**
  1. **Сейчас:** убрать бонусы за обязательные гейты (sweep/displacement/MSS для reversal, BOS для continuation). Оставить бонусы за *необязательные* улучшатели: volume, MTF, session, ATR-режим, context. Переименовать поле `p_tp` → `setup_score` в rules-режиме, чтобы не смешивать с калиброванной вероятностью.
  2. **После накопления 100+ исходов:** калибровка — логистическая регрессия или isotonic на `SetupFeatures.to_vector()` → win/loss; калиброванное p использовать в EV/Kelly; хранить calibration curve в БД.
  3. Пороги `min_p_tp` пересмотреть после калибровки (калиброванное p обычно уже разбросано 0.35–0.65 — тогда 0.30/0.40/0.50 начнут реально резать).
- **Критерий приёмки:** распределение rules-score после шага 1 имеет разброс (гистограмма в funnel-логе); юнит-тест: reversal без volume/MTF-сопровождения получает score < порога 0.50 и блокируется `MIN_P_TP`.

### [LG-08] Тройной учёт HTF-alignment (hard gate + additive + multipliers) + мёртвый код
- **Где:** Phase 1.45, Feature Builder (`mtf_aligned`, `htf_alignment_score`, `htf_bias_penalty`), Probability Engine.
- **Суть:** (1) hard gate режет mismatch; (2) additive `MTF aligned: +2` — при включённом гейте почти всегда true → константа; (3) multiplier `htf_bias_penalty = 0.8` для reversal mismatch — **недостижим**, т.к. mismatch уже заблокирован гейтом (dead code path).
- **Изменение:** оставить **один** активный механизм на конфигурацию:
  ```python
  if config.htf_hard_gate:
      # multipliers htf_bias_penalty/htf_alignment_score — пропускать (не применять)
  else:
      # применять multipliers, hard gate — выключен
  ```
  Убрать additive `+2 MTF aligned` при включённом гейте (или делать его пропорциональным strength: WEAK alignment +0.5, MODERATE +1.0, STRONG +2.0).
- **Критерий приёмки:** при `htf_hard_gate=true` изменение `htf_bias_penalty` не влияет на результат (тест); при `false` — влияет.

### [LG-09] Асимметрия `min_p_tp`: SELL 0.40 vs BUY 0.30 — без доказательной базы
- **Где:** ProbabilityConfig.
- **Суть:** шортам требуется более высокая вероятность. Обоснования в аудите нет. Если это следствие «крипта растёт» — это режимный аргумент, а не структурный; в медвежьем рынке аргумент инвертируется.
- **Изменение:** до бэктеста — унифицировать (например, 0.35 обоим направлениям); асимметрию вводить только после сравнения PF long/short на истории исходов. Добавить метрики в daily report: winrate/PF по направлениям.
- **Критерий приёмки:** конфиг содержит одно значение или значения, подтверждённые расчётом из `signal_outcomes` (скрипт-обоснование в репозитории).

### [LG-10] Корреляционный блок vs портфель BTC/ETH/SOL: риск вырождения в «одну позицию по BTC»
- **Где:** Phase 7 execution filters (`CORRELATION_BLOCKED`), risk limits.
- **Суть:** пары BTC/ETH/SOL в нормальной рыночной фазе коррелируют 0.8–0.95. При открытом BTC long почти любой ETH/SOL long сигнал будет отклонён корреляцией → `max_long_positions=3` и `max_positions_total=5` фактически недостижимы в лонг; в шорт — аналогично.
- **Изменение:** (а) сделать порог корреляции явным параметром (`CORRELATION_BLOCK_THRESHOLD`, default, например, 0.9) и считать корреляцию по rolling-окну доходностей (не константой); (б) разрешать коррелированный вход, если суммарный портфельный риск после него ≤ `max_portfolio_risk_pct` — риск-лимит и есть правильный инструмент, а не счётчик символов; (в) убрать дублирование: correlation-block **или** direction limits, не оба.
- **Критерий приёмки:** на истории сделок за период высокой корреляции количество `CORRELATION_BLOCKED` снижается до осмысленного уровня; портфельный риск при этом не превышает 3.7% (тест на синтетических данных).

### [LG-11] Семантика «сигнал vs позиция» не определена: `max_active_signals=10` vs `max_positions_total=5`
- **Где:** Phase 0.2 (`get_active_signals_count`) ↔ Phase 0.2c (`get_open_outcomes`).
- **Суть:** если сигнал → outcome 1:1, лимит 5 всегда срабатывает раньше 10, и `PORTFOLIO_MAX_ACTIVE` недостижим. Если не 1:1 — что такое «active signal» без позиции? В документе не описано. `CHECK-CODE`.
- **Изменение:** определить: `active_signals` = сигналы без outcome; `open_outcomes` = позиции. Оставить оба лимита, но: `max_active_signals` должен быть ≥ `max_positions_total` и покрывать «в полёте» между сигналом и открытием; добавить в daily report обе метрики.
- **Критерий приёмки:** документация в коде (docstring) + тест, где 6 активных сигналов без outcomes → `PORTFOLIO_MAX_ACTIVE`, 5 outcomes → `POSITION_LIMIT_HIT` (порядок проверок детерминирован).

### [LG-12] Правило разметки неоднозначных исходов (TP и SL внутри одной свечи) не задокументировано
- **Где:** `scheduler/outcome_tracker.py`. `CHECK-CODE`.
- **Суть:** если внутри одной свечи коснулись и TP, и SL — исход не определён. Если трекер считает такое победой, калибровка P(TP) завысится; если похожих случаев много — систематически. Особенно критично для 4h-свечей и широких SL (см. LG-01).
- **Изменение:** консервативное правило по умолчанию: ambiguous → **loss** (или 0.5R, но лучше loss — консерватизм в обучении), плюс колонка `ambiguous=1` в outcomes, чтобы можно было оценить долю. В отчёте: count ambiguous.
- **Критерий приёмки:** юнит-тест на OHLCV-фикстуру, где low < SL < TP < high в одной свече → outcome=loss, flag=ambiguous.

### [LG-13] Kelly-режим не может увеличить риск: `kelly *= ...; risk_pct = min(kelly*100, base_risk_pct)`
- **Где:** `risk/engine.py` position sizing.
- **Суть:** при p=0.6, b=2.0 → Kelly = (0.6×2 − 0.4)/2 = 0.4 → `min(40, 1.0) = 1.0`. Kelly работает только на понижение. Если это осознанный «downside-only Kelly» — ок, но тогда он не оправдывает сложности; если задумывался как усилитель сильных сетапов — баг.
- **Изменение (выбрать):** (а) честный half-Kelly с потолком `max_risk_pct` (2.0): `risk_pct = min(0.5*kelly*100, max_risk_pct)`; (б) оставить как есть, переименовать режим в `fixed_with_kelly_floor`, убрать из документации слово Kelly. Учесть связку с LG-07: Kelly от некалиброванного p — опасен (p=0.85 после клампа даёт Kelly 0.72 → при варианте (а) риск упирается в cap 2% всегда — cap спасает, но осознанно).
- **Критерий приёмки:** таблица в тестах: (p, b) → risk_pct для обоих режимов; поведение соответствует выбранной семантике.

### [LG-14] `sl_distance < 1% → risk_pct × 1.1` — рост риска при узком SL
- **Где:** `risk/engine.py` adjustments.
- **Суть:** узкий SL → позиция больше по размеру; множитель ×1.1 дополнительно увеличивает риск именно на сделках с тесным стопом. При гэпе/слиппедже через стоп реальный убыток > 1.1× планового. Обоснование «выравнивание $-риска» неверно: $-риск и так фиксирован `risk_budget = equity × risk_pct`; distance влияет на size, не на $-риск.
- **Изменение:** убрать ×1.1; вместо этого — **cap на notional/плечо** (`max_notional_pct_of_equity`, например 25%), чтобы узкие стопы не порождали экстремальные размеры. Проверить связку с min-notional gate (A10).
- **Критерий приёмки:** sizing-тест: SL 0.8% vs SL 2.5% при прочих равных → одинаковый risk_pct (или разный только по волатильным множителям), notional ограничен cap'ом.

### [LG-15] Analytical Overlays влияют на риск до валидации (scenario_adj 0.6–1.2, stability_adj 0.7–1.15)
- **Где:** Phase 1.55–1.7 → Risk Engine (`scenario_adj`, `stability_adj`).
- **Суть:** суммарный диапазон множителей ≈ 0.42–1.38 к риску из эвристических оверлеев без подтверждённой предиктивной силы. Это больше, чем эффект многих гейтов. Сами оверлеи (thesis/scenario) — самые сложные и наименее проверяемые компоненты системы.
- **Изменение:** флаг `OVERLAYS_AFFECT_SIZING` (default `false`); при `false` — oверлеи пишутся в trace/analytics, но `scenario_adj = stability_adj = 1.0`. Логировать counterfactual (что бы было при включении). Включать только после бэктеста: сравнение PF с/без оверлеев на одной выборке.
- **Критерий приёмки:** при `false` значения оверлеев в trace сохраняются, sizing не меняется (тест); фигурирует в daily report счётчик «риск скорректирован оверлеями: 0».

### [LG-16] HTF-voting описан для 3 голосов, используется 4 (W1/D1/H4/H1); H1 при скане 1h — циркулярность
- **Где:** `market_structure/htf_bias_v2.py`.
- **Суть:** правила «3/3 → STRONG, 2/3 → MODERATE» не покрывают 4 голоса (что есть 2/4? MODERATE или NEUTRAL?). Дополнительно H1 входит в голосование и одновременно является сигнальным TF при скане 1h → bias частично подтверждает сам себя.
- **Изменение:** явная матрица для 4 голосов (пример):
  ```python
  votes = {"W1": v1, "D1": v2, "H4": v3}   # H1 исключить из голосования
  # 3/3 → STRONG; 2/3 → MODERATE; 1/3 → WEAK; 0/3 → NEUTRAL
  ```
  H1 оставить только для zone classification (как и указано §3 аудита), не для voting. Если нужен H1-голос — снижать его вес (×0.5).
- **Критерий приёмки:** таблица тестов на все комбинации голосов; скан 1h с идеально развёрнутым H1 не получает «самоподтверждение» (bias без H1 ≠ bias с H1 в тесте).

### [LG-17] Fees/slippage заложены 0.05% на сторону (0.1% round trip) — занижено для market-исполнения
- **Где:** Risk Engine (round_trip_cost).
- **Суть:** taker ~0.05% × 2 = 0.1% + slippage на входе и на стопе (стоп — маркет-ордер в момент волатильности, slippage 0.02–0.1%) → реалистично 0.12–0.18%. Заниженная оценка **завышает** RR → пропускаются сделки, которые на деле EV<0. Занижение cost — это ошибка в опасную сторону, противоположную консервативной.
- **Изменение:** параметры `FEE_PCT=0.05`, `SLIPPAGE_PCT=0.05` (round trip = 2×(fee+slippage) = 0.2%). После накопления исходов — калибровать slippage по фактическим ценам входа/выхода из outcome tracker (если хранятся).
- **Критерий приёмки:** параметры в конфиге; тест RR-гейта с граничной сделкой (RR 2.01 при cost 0.2% → блок; при 0.1% → проход) — зафиксировать выбранное поведение.
