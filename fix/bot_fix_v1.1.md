## P0-1 — `reclaim_bars` в MSS-классификации берётся не из того sweep

### Файлы
- `scheduler/scanner.py` (примерно строка 486-492, участок перед вызовом `analyze_structure()`)
- `market_structure/structure.py`, функция `classify_choch()` (строка ~129-230)

### В чём баг

`scanner.py` вычисляет `reclaim_bars` **до** вызова `analyze_structure()`, произвольно беря
первый валидный sweep из списка:

```python
# scheduler/scanner.py, текущий код
_reclaim = 0
if sweeps:
    _valid_sw = [s for s in sweeps if s.is_valid]
    if _valid_sw:
        _reclaim = _valid_sw[0].reclaim_candles   # ← первый по порядку в списке
```

`sweeps` возвращается функцией `detect_sweeps()` (`liquidity/sweep.py`), которая проходит
по барам от старых к новым (`for i in range(len(data))`) и добавляет sweep-события в список
в этом же порядке. Значит **`_valid_sw[0]` — это самый старый валидный sweep в 50-баровом
окне поиска**, а не обязательно тот, что реально связан с текущим CHoCH.

Внутри `classify_choch()` (`market_structure/structure.py`) есть **отдельный, независимый**
поиск нужного sweep — по направлению (противоположному CHoCH) и по причинному окну
(`max_causal_bars=10`):

```python
# market_structure/structure.py, classify_choch()
for s in sweeps:
    sweep_dir = "buy" if s.type == "bullish" else "sell"
    choch_dir = "buy" if choch.type == "bullish" else "sell"
    if sweep_dir == choch_dir:
        continue
    if choch.candle_index >= 0 and s.candle_index >= 0:
        delta = choch.candle_index - s.candle_index
    else:
        delta = 0
    if 0 <= delta <= max_causal_bars:
        if matching_sweep is None or delta < bars_since:
            matching_sweep = s
            bars_since = delta
```

Но финальная проверка MSS использует **не** `matching_sweep.reclaim_candles`, а тот самый
внешний параметр `reclaim_bars`, переданный из `scanner.py`:

```python
is_mss = (
    choch.has_sweep_reference
    and displacement_atr >= 0.2
    and reclaim_bars <= 2      # ← это _valid_sw[0].reclaim_candles, НЕ matching_sweep!
)
```

**Итог**: даже если `matching_sweep` найден правильно (нужное направление, свежий, быстрый
reclaim=1), условие `reclaim_bars <= 2` сверяется со значением от **другого**, произвольного
(обычно более старого) sweep. Если у этого старого sweep `reclaim_candles > 2` (типично для
менее чётких/старых свипов) — `is_mss` не срабатывает **независимо от качества настоящего
matching_sweep**. В окне из 50 баров, где sweep-событий обычно несколько, вероятность
случайного совпадения `_valid_sw[0]` с настоящим `matching_sweep` низкая — отсюда
систематический (не эпизодический) провал MSS-классификации почти на всех попытках.

Это, судя по всему, главный кандидат на причину `mss_none` = 12,179 отказов и
резкого падения MSS detection rate с исторических 43-57% (см. `logic_3.md` из более раннего
аудита этого же проекта) до практически 0% сейчас.

### Что нужно изменить

Убрать `reclaim_bars` как **внешний** параметр, который вычисляется вслепую до вызова
`classify_choch()`. Вместо этого — вычислять reclaim **из найденного `matching_sweep`**,
внутри самой функции, после того как он определён.

**Вариант A (минимальное изменение, рекомендуется)** — в `market_structure/structure.py`,
внутри `classify_choch()`, после блока `if matching_sweep is not None:` заменить источник
`reclaim_bars`:

```python
if matching_sweep is not None:
    choch.has_sweep_reference = True
    choch.causality_score = calc_causality(bars_since)
    reclaim_bars = matching_sweep.reclaim_candles   # ← ДОБАВИТЬ эту строку
    ...
```

и убедиться, что дальше по коду (в блоке измерения displacement и в финальном `is_mss =`)
используется именно это локально переопределённое значение, а не аргумент функции.
Учитывая, что Python позволяет переприсвоить параметр функции локально — этого может быть
достаточно, но нужно явно проверить, что `reclaim_bars` больше нигде выше по коду не
используется до этой точки таким образом, что переопределение сломает что-то ещё
(например, попадание в `choch.reclaim_bars = reclaim_bars`, которое стоит ДО этого блока —
эту строку тоже нужно передвинуть ниже, после переопределения, либо присвоить `choch.reclaim_bars`
повторно после обновления).

**Вариант B (чище архитектурно)** — убрать параметр `reclaim_bars` из сигнатуры
`classify_choch()` и `analyze_structure()` целиком, а также убрать блок предварительного
вычисления `_reclaim` в `scanner.py` (строки с `_valid_sw[0].reclaim_candles`). Тогда
`classify_choch()` сам вычисляет reclaim из `matching_sweep`, если он найден, и `0`/`None` —
если не найден (что и так проваливает `has_sweep_reference`, а значит `is_mss` не сработает
по этой причине, а не по неверному reclaim).

### Как проверить

1. Добавить временный debug-лог в `classify_choch()`, печатающий `matching_sweep.candle_index`,
   `matching_sweep.reclaim_candles` и старое значение переданного `reclaim_bars` — прогнать на
   реальных исторических данных (BTC/ETH за последние несколько дней) и убедиться, что после
   фикса эти два числа чаще совпадают, а `is_mss` начинает срабатывать заметно чаще, чем 0%.
2. Прогнать `scripts/measure_rejection_rate.py` (или аналог, если переименован) на тех же
   4 символах, что в `logic_3.md` (BTC, ETH, SOL, DOGE), сравнить MSS rejection rate до/после:
   ожидаемый ориентир — возврат к диапазону 43-60% (не обязательно точно тем же числам, рынок
   изменился, но порядок величины должен быть похож, а не 96-100%, как сейчас подразумевает
   ваша воронка).
3. Не менять пороги `displacement_atr >= 0.2` или `reclaim_bars <= 2` в рамках этого фикса —
   сначала нужно увидеть реальный detection rate с ПРАВИЛЬНЫМ reclaim, и только потом решать,
   нужно ли трогать сами пороги (см. процесс из предыдущих раундов: данные → решения, не
   наоборот).

## P1-1 — SL dead zone: "релакс" не устраняет проблему при ATR 4.0-5.0%

### Файл
`risk/engine.py`, метод оценки SL (проверки для `SL_TOO_WIDE` и `SL_ATR_CONFLICT`)

### В чём проблема

Текущий код:

```python
dynamic_sl_max = min(max(sl_absolute_max_pct, atr_pct * 2.2), 8.0)
# гейт 1: если sl_distance_pct > dynamic_sl_max → reject SL_TOO_WIDE

min_sl_from_atr = atr_pct * 2.0
if min_sl_from_atr > dynamic_sl_max:
    min_sl_from_atr = dynamic_sl_max   # "релакс"
if sl_distance_pct < min_sl_from_atr:
    return RiskDecision(should_trade=False, ...)  # reject SL_ATR_CONFLICT
```

Расчёт для ATR ∈ (4.0%, 5.0%] (полностью достижимый диапазон — `volatility_max_atr_percent`
= 5.0%, подтверждено в `config/settings.py`):

- `dynamic_sl_max` = 8.0% (cap уже достигнут при ATR > 3.636%)
- `min_sl_from_atr` (до релакса) = ATR × 2.0, что при ATR=4.5% даёт 9.0% > 8.0% (cap)
- После "релакса" `min_sl_from_atr` становится **равен** `dynamic_sl_max` = 8.0%

Значит валиден только `sl_distance_pct`, находящийся **одновременно** `<= 8.0%` (гейт 1) и
`>= 8.0%` (гейт после релакса) — то есть ровно 8.0%, единственная точка на непрерывной
величине. На практике это почти никогда не выполняется точно → сделки с ATR в этом диапазоне
почти всегда отклоняются на одном из двух гейтов. "Релакс" не расширяет диапазон, а лишь
схлопывает его в точку — по факту баг не устранён, просто изменилось название причины отказа
в логах.

### Что нужно изменить

Выбрать один из двух вариантов (нужно явное решение, какой предпочтителен для стратегии):

**Вариант A** — убрать hard cap 8.0% совсем:
```python
dynamic_sl_max = max(sl_absolute_max_pct, atr_pct * 2.2)   # без min(..., 8.0)
```
Так как множитель верхней границы (2.2) больше множителя нижней границы (2.0), dead zone
математически невозможна при любом ATR.

**Вариант B** — оставить cap, но синхронно сузить `volatility_max_atr_percent` в
`config/settings.py` до значения, где cap физически не достижим относительно floor:
```python
# floor = ATR × 2.0, cap = 8.0 → floor становится проблемой при ATR > 4.0%
# значит нужно: volatility_max_atr_percent <= 4.0
VOLATILITY_MAX_ATR_PERCENT = 4.0   # было 5.0
```

Рекомендация: **Вариант A** — он не требует трогать фильтр волатильности (который сам по
себе может быть предметом отдельной калибровки) и является более общим/устойчивым фиксом.

### Как проверить

Юнит-тест: для ATR в диапазоне [0.3%, 8.0%] с шагом 0.1% (даже за пределами текущего
volatility filter — на случай, если фильтр позже расширят) проверить, что
`floor(ATR) <= ceiling(ATR)` всегда выполняется (валидный диапазон SL не пуст). Добавить
этот тест в `tests/`, чтобы дефект не вернулся при будущих правках констант.

## P1-2 — EV-гейт реально работает только в Kelly-режиме, а бот по умолчанию в Fixed-режиме

### Файлы
`risk/engine.py` (расчёт риска), `config/settings.py:703` (`risk_mode` default)

### В чём проблема

```python
_risk_mode = getattr(config, 'risk_mode', 'fixed')   # default = 'fixed'

if _risk_mode == 'fixed':
    risk_pct = self.base_risk_pct        # ← нет проверки на EV/P(TP) вообще
else:
    kelly = (p * b - q) / b
    if kelly <= 0:
        return RiskDecision(should_trade=False, ...)   # ← EV-проверка только здесь
```

`kelly <= 0` математически эквивалентно `EV <= 0`, но эта проверка целиком находится
в ветке `else`, которая не выполняется, если `risk_mode == 'fixed'` — а это дефолт.
То есть **в Fixed-режиме нет вообще никакой проверки на отрицательное математическое
ожидание сделки**. Единственная вероятностная защита — `min_p_tp` (Phase 3.1, пороги
30%/40%/50% по направлениям), который не зависит от фактического R:R конкретной сделки.

### Что нужно сделать

1. **Сначала проверить**, какой `RISK_MODE` реально стоит в проде (`.env`/деплой-конфиг).
   Если там `RISK_MODE=kelly` (или что угодно кроме `fixed`) — эта проблема неактуальна,
   можно понизить приоритет до P2.
2. Если `RISK_MODE=fixed` в проде — добавить явную EV-проверку и в fixed-ветку тоже:
```python
if _risk_mode == 'fixed':
    ev = probability.p_tp * rr_ratio - (1 - probability.p_tp)
    if ev <= 0:
        return RiskDecision(should_trade=False, rejection_reason=f"negative EV, ev={ev:.3f}")
    risk_pct = self.base_risk_pct
```
3. Обновить маппинг в `scanner.py` (диспетчер `_rcode` по `rejection_reason`), где сейчас
   `NEGATIVE_EV` матчится только по подстроке `"kelly="` — добавить также матчинг по
   `"negative EV"`, иначе новый reject останется без правильного reason_code и упадёт в
   дефолтный `SL_TOO_WIDE` (искажая статистику воронки).

### Как проверить

После фикса — в fixed-режиме прогнать несколько тестовых сценариев с заведомо плохим R:R и
низким P(TP) (например, P(TP)=25%, RR=2.0 → EV = 0.25×2 - 0.75 = -0.25 < 0) и убедиться, что
сделка отклоняется с новым reason_code, а не проходит.

## P2-2 — `block_neutral_htf` — мёртвый флаг

### Файлы
