Ты работаешь как senior Python quant developer, специализирующийся на backtesting и 
эвалюации торговых стратегий.

КОНТЕКСТ

В проект недавно внесены изменения в логику расчёта SL/TP (см. предыдущие задачи 1-6: 
унификация entry, structural SL, min/max SL distance, проверка RR, новостной фильтр, 
stop hunt buffer). Перед тобой задача — построить инфраструктуру бэктеста с нуля и 
провести оценку, которая покажет:
1. Как новая логика в целом работает в сравнении со старой.
2. Какой вклад в результат вносит КАЖДАЯ из задач 1-6 по отдельности.

В проекте сейчас НЕТ готового backtesting-движка — тебе нужно создать его самостоятельно. 
Перед началом изучи актуальный код strategy/signal_engine.py, scheduler/scanner.py, 
risk/dynamic_risk.py, config/settings.py, чтобы понять реальную механику генерации сигналов, 
а не полагаться на описания из прошлых задач (код мог отличаться от того, что обсуждалось).

ЭТАП 0. Источник исторических данных

В проекте нет готового источника исторических OHLCV. Прежде чем писать движок:
- Проверь, есть ли в коде уже интеграция с какой-либо биржей (ccxt, binance-connector, 
  готовые клиенты API и т.п.) — если есть, используй её для загрузки данных, не добавляй 
  новую зависимость без необходимости.
- Если интеграции нет, выбери источник самостоятельно (например, Binance public API 
  через ccxt — он не требует ключей для исторических klines) и обоснуй выбор в отчёте.
- Учти лимиты rate-limit биржевого API при массовой загрузке данных за длительный период.
- Загрузи и закэшируй данные локально (parquet/csv), чтобы не дёргать API повторно при 
  каждом прогоне бэктеста.
- Зафиксируй в отчёте: какие именно символы, таймфреймы и период истории были загружены, 
  и почему выбран именно этот набор (например: топ-N по объёму торгов на споте, период 
  минимум 6-12 месяцев, включающий разные рыночные режимы — тренд/флэт/высокая волатильность).

ЭТАП 1. Архитектура backtesting-движка

Создай движок, который:
- Прогоняет исторические OHLCV через ТЕ ЖЕ функции, которые использует live-бот 
  (signal_engine, scanner, dynamic_risk) — не дублируй логику упрощённой копией, иначе 
  результат бэктеста не будет отражать реальное поведение бота.
- Корректно симулирует механику исполнения: 
  - SL и TP проверяются по high/low следующих свечей после входа, а не только по close;
  - если в одной свече SL и TP оба теоретически достижимы (свеча с большим диапазоном), 
    закладывай консервативное допущение — берётся тот уровень, который должен был 
    сработать раньше по ходу свечи (если есть доступ к более мелкому таймфрейму для 
    этой свечи, используй его для уточнения порядка; если нет — явно укажи в отчёте, 
    какое допущение использовано, и пометь такие сделки отдельным флагом, чтобы их можно 
    было исключить из чувствительного анализа);
  - учитывай комиссию биржи (укажи, откуда взято значение — конфиг проекта или 
    стандартная ставка биржи) и проскальзывание (slippage) на входе и выходе — 
    хотя бы базовую модель (фиксированный % или на основе спреда, если данные доступны);
  - НЕ допускай look-ahead bias: на каждом баре движок должен видеть только данные 
    до этого бара включительно, не будущие свечи.
- НЕ позволяй себе упрощать или "срезать углы" в реализации механики исполнения ради 
  скорости — если есть выбор между точностью симуляции и простотой кода, выбирай точность, 
  и явно отметь в отчёте места, где точность всё же пришлось принести в жертву и почему.

ЭТАП 2. Дизайн сравнения (A/B/n)

Тебе нужно прогнать НЕ ОДИН, а несколько вариантов бота на одних и тех же исторических 
данных (одинаковый набор символов, период, таймфреймы — иначе сравнение некорректно):

1. BASELINE — логика ДО внесения задач 1-6 (старая версия расчёта SL/TP). Если в git 
   истории есть коммит до этих изменений — используй его. Если изменения уже необратимо 
   смешаны в текущем коде, восстанови baseline-поведение через конфигурационные флаги 
   или временный возврат старой ветки логики — спроси у меня, если это не очевидно как 
   сделать чисто.
2. TASK_1_ONLY — baseline + только унификация entry (задача 1).
3. TASK_2_ONLY — baseline + только structural SL (задача 2).
4. TASK_3_ONLY — baseline + только min/max SL distance (задача 3).
5. TASK_4_ONLY — baseline + только финальная проверка RR (задача 4).
6. TASK_5_ONLY — baseline + только новостной фильтр (задача 5), если эта задача была 
   реализована полноценно (а не как заглушка) — если заглушка, пропусти этот вариант 
   и явно укажи причину в отчёте.
7. TASK_6_ONLY — baseline + только stop hunt buffer (задача 6).
8. FULL — все задачи 1-6 включены вместе (текущее состояние кода).

Если изолировать задачи технически сложно (например, задачи 2 и 6 физически связаны, 
так как buffer применяется только к structural SL) — объясни зависимость в отчёте и 
предложи ближайший технически корректный вариант изоляции (например, TASK_2_ONLY без 
buffer, отдельным флагом).

ЭТАП 3. Метрики

Для КАЖДОГО из 8 вариантов (baseline, 6 изолированных, full) посчитай:
- Win rate (%)
- Средний R:R по факту исполненных сделок (не теоретический, а реальный — по факту 
  срабатывания SL/TP)
- Profit factor (сумма прибыли / сумма убытков)
- Общее количество сигналов сгенерировано vs количество отклонено (reject) — с разбивкой 
  по причине reject, если есть несколько причин
- Максимальная просадка (max drawdown, %)
- Средняя продолжительность сделки (время от entry до SL/TP)
- Распределение по причине закрытия: SL hit / TP hit / TP partial (если есть несколько 
  целей) / не закрыто до конца периода теста
- Sharpe ratio или аналог (если в проекте уже есть похожая метрика — используй её 
  методологию для консистентности с другими отчётами)

ЭТАП 4. Сравнительный анализ

- Сравни FULL против BASELINE по всем метрикам — это основной результат.
- Сравни каждый TASK_N_ONLY против BASELINE отдельно — покажи вклад каждой задачи 
  изолированно (taблица: метрика / baseline / task1 / task2 / ... / task6 / full).
- Укажи, есть ли задачи, которые в изоляции ухудшают метрики, но в комбинации (FULL) 
  работают лучше за счёт взаимодействия с другими задачами (например, structural SL 
  без RR-фильтра может давать худший profit factor, чем с фильтром — это ожидаемо и 
  важно показать явно).
- Укажи statistical significance, если выборка сигналов достаточно большая для этого 
  (минимум использовать доверительные интервалы для win rate; если знаешь подходящий 
  тест значимости для финансовых рядов — используй, но не выдумывай ложную строгость 
  на маленькой выборке).
- Отдельно разбей результаты по рыночному режиму, если период теста охватывает разные 
  условия (тренд / флэт / высокая волатильность) — изменения в SL/TP логике могут 
  по-разному работать в разных режимах.

ЭТАП 5. Контроль качества бэктеста

Прежде чем доверять результатам, проверь и укажи в отчёте:
- Нет ли survivorship bias в выборе символов (например, если тестируешь только на 
  токенах, которые сейчас в топе по объёму — это может скрывать делистнутые/упавшие 
  в ноль монеты, которые исказили бы реальную картину).
- Совпадает ли количество и распределение сгенерированных сигналов в бэктесте с тем, 
  что логирует live/paper режим бота на тех же исторических данных (если есть 
  возможность сверить хотя бы на небольшом отрезке) — это базовая проверка, что 
  бэктест-движок действительно эквивалентен боевой логике, а не разошёлся с ней.
- Достаточен ли объём данных (количество сделок на вариант) для того, чтобы выводы 
  не были шумом — если сделок слишком мало (десятки), явно предупреди об этом в 
  отчёте, а не подавай результат как окончательный.
