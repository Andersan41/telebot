# Инструкция исполнителю: задача из `plan/improvements/`

Ты — инженер. Тебе дают **один файл** из `plan/improvements/` (например,
`plan/improvements/A4-cooldown-db.md`). Твоя работа — выполнить эту задачу
**целиком за один проход**: код + тесты + проверка зелёного pytest + отметка
«сделано» в плане. Никаких других задач за этот же проход **не** трогаешь.

---

## Контекст проекта (минимум, который нужен)

- Python 3.11+, async, Telegram-бот для торговых сигналов.
- Стек: `python-telegram-bot`, `ccxt.async`, `SQLAlchemy 2.0 + aiosqlite`,
  `pandas-ta`, `aiohttp`, `APScheduler`, `loguru`.
- Тесты — `pytest` + `pytest-asyncio` + `aioresponses`. Раннер: `pytest -v`.
  Все существующие тесты лежат в `tests/`.
- Архитектура и точки расширения описаны в `plan/01-architecture.md`,
  `plan/02-main.md` … `plan/16-commands.md`. Прочти соответствующий раздел
  **перед** редактированием кода, упомянутого в задаче.
- Корневой `AGENTS.md` содержит краткий бриф (архитектура, тесты, gotchas).
  Загляни туда, если что-то непонятно про общее устройство.

---

## Алгоритм (выполняй строго по шагам)

1. **Прочитай файл задачи целиком.** В каждом файле есть блоки:
   - Шапка `Статус / Приоритет / Зависимости`.
   - `Цель`.
   - `Файлы и точные места` — таблица с тем, что трогать.
   - `Предусловия` — что должно быть до старта.
   - `Пошагово` — основной чеклист.
   - `Edge cases` — ловушки.
   - `Готовность` — критерии «сделано».
   Не пропускай ни один блок. Если зависимости не выполнены — см. п.9.

2. **Сверь `Файлы и точные места` с реальностью.**
   Для каждого `file:line` из таблицы открой файл и убедись, что строка/функция
   реально там. Номера могут «уехать» на ±1–3 строки между версиями — это
   **нормально**; ориентируйся на содержимое (имя функции, текст). Если строка
   ушла далеко (>10) или функция отсутствует — **остановись и спроси** (п.9).

3. **Сверь `Предусловия`.** Если что-то не выполнено (например, в задаче F4.1
   написано «требует A1» и A1 ещё `🔴`) — **остановись и спроси** (п.9).

4. **Выполни `Пошагово`.** Каждый шаг — отдельная правка в одном файле.
   - Не объединяй несвязанные правки.
   - Не редактируй файлы, которых нет в таблице `Файлы и точные места`,
     **кроме** тестов (их можно добавлять/расширять всегда).
   - Не «улучшай по дороге» соседний код, который не относится к задаче.
   - Когда в шаге написан код-блок — используй его буквально, имена переменных
     и сигнатуры не переименовывай.

5. **Напиши тесты.** Если задача уже содержит готовые тесты в блоке `Тест` /
   `Тесты` / `Готовность` — используй их буквально. Если задача не описывает
   тест явно — напиши хотя бы один pytest-кейс, который ловит регрессию
   на основной шаг. Тесты кладутся в существующий `tests/test_*.py`, который
   соответствует тематике (см. `tests/` — `test_scanner.py`, `test_context.py`,
   `test_signal.py`, `test_config.py`, и т.д.).

6. **Запусти тесты.** Сначала точечно — только новые/изменённые:
   ```bash
   pytest tests/<имя_файла>.py -v
   ```
   Затем — **весь** набор:
   ```bash
   pytest -v
   ```
   Зелёное полностью? Иди дальше. Что-то красное? Чини **причину**, не маскируй
   ассертами. Запрещено: коммитить со `xfail`, `skip` без обоснования, или с
   правкой ассертов под удобный результат.

7. **Проверь `Готовность`.** Пройди по списку критериев в конце файла задачи
   и убедись, что каждый закрыт (ручные шаги — например, «sqlite3 …», «curl …»,
   «запусти бота» — выполни, если можешь; если нельзя — отметь в финальном
   ответе и предупреди пользователя).

8. **Отметь «сделано» в трёх местах**:

   8.1. **В файле задачи** (`plan/improvements/<X>-…md`): в шапке поменяй
   `> **Статус**: 🔴 не сделано` → `> **Статус**: ✅ сделано`.

   8.2. **В `plan/17-improvements.md`** — найди соответствующую строку в одной
   из таблиц («Архитектура» / «Тесты / DX» / «Функциональность») и заменить
   ничего не нужно (там нет колонки «статус»). Но **в секции
   `## Шпаргалка по приоритетам`** удали имя задачи из той строки приоритета,
   где она числится. Если задача была единственной в строке — удали строку.

   8.3. **В `plan/00index.md`** — в нижней таблице «Спецификации задач из
   бэклога (раздел 17)» в колонке `Приоритет` рядом со статусом-эмодзи добавь
   `✅` перед эмодзи приоритета (например, было `🟠 high` — стало `✅ 🟠 high`).
   Если **все** задачи в бэклоге стали `✅` — поменяй статус строки 17 в
   верхней таблице с `🔴` на `✅`.

9. **Когда останавливаться и спрашивать (не догадываться):**
   - Файл задачи ссылается на код/функцию, которой нет.
   - Зависимая задача (`Зависимости:` в шапке) ещё `🔴`.
   - Шаг говорит «согласуй с владельцем» — **не пропускай**, действительно
     согласуй.
   - Поведение, описанное в задаче, конфликтует с реальным кодом (например,
     задача описывает функцию-синхронную, а в коде она уже async).
   - Тест из задачи не проходит даже после корректной реализации шагов —
     не «подгоняй» под него, опиши расхождение.

10. **Финальный ответ пользователю** — короткий, по делу:
    - Имя задачи: `A4 — Cooldown в БД`.
    - Что изменил: список файлов с краткой пометкой.
    - Тесты: какие добавил, сколько прошло (`X passed`).
    - Ручные шаги из `Готовность`, которые НЕ выполнил (если есть).
    - Где поставил `✅` (три места из шага 8).
    - Если задача не закрыта — **честно** скажи это и поясни почему,
      статус **не меняй**.

## Жёсткие правила

- **Одна задача за проход.** Не открывай вторую, пока первая не закрыта.
- **Не меняй файлы, не указанные в `Файлы и точные места`** (исключение —
  тесты и индексные файлы из шага 8 при пометке «сделано»).
- **Не амни коммиты и не делай force-push.** Создавай новый коммит.
- **Не отключай тесты** через `xfail`/`skip`/удаление, чтобы «было зелёное».
- **Не используй `--no-verify`** и прочие шорткаты в обход хуков.
- Если в задаче есть `⚠️` — это не декорация, это предупреждение. Прочти
  и учти.
- **Комментарии в коде — только когда поясняешь «почему» неочевидное.**
  Не пиши «# увеличиваем X на 1». См. также общие конвенции в `AGENTS.md`.
